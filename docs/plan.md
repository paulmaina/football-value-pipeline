# Plan: independent research model, market tier and reconciled master shortlist

Agreed with Paul on 9–10 Nov 2026. The working copy is also kept as a claude.ai doc; this file is the repo copy, so any Claude Code session (local or cloud) starts with the same context.

## Goal

The pipeline holds two deliberately different opinions and lets the master shortlist weigh them.

| List | Its job | Probabilities come from | Must never use |
| --- | --- | --- | --- |
| Value shortlist | Find bets where the research disagrees with the market | Match history, ESPN results, Understat xG, domestic stats carried into UCL/UEL | Any bookmaker odds |
| Cagey tier | Safest bets, priced as close to Pinnacle as possible | Pinnacle 1X2, totals and main AH line, plus the narrow-margin correction | Research form or news |
| Master shortlist | Best bets after the two views are compared | Both lists' probabilities | A third model of its own |

Where bets are placed is a separate setting: all lists bet at Pinnacle only (`shortlist_quote_policy.json`). That has no effect on whether a model is independent. The published score grid already includes 70% Pinnacle, so it is a benchmark only and can never power the value model.

## Ground rules

- Nothing reaches production until it beats the current version on matches it has never seen, by more than noise. Mixed or small results: report them and keep the current rule.
- Pre-kickoff data only. Every test uses only what was known before the match.
- Decide the test before the data: candidate, metrics and subsets are declared before the holdout is scored.
- Shadow first. New logic writes beside the live files until it passes.
- One change per list at a time.
- Independence is enforced: the value model has an explicit input schema, and a test changes every odds field and checks its probabilities stay identical. Only the selection layer uses the Pinnacle offer, to calculate expected return and qualify a bet.

## Release gate

- Primary metric: log loss on AH settlement across all lines; draw-sensitive subset AH 0 and ±0.5.
- Calibration tolerance, v2 (decided 11 Nov 2026): the candidate's home and away logistic calibration slopes (logit P(outcome) = a + b logit(p), fitted per outcome on its 1X2 forecasts) are both between 0.90 and 1.10, and no outcome probability band (home, draw or away, in tenths of probability, at least 30 matches) fails. A band fails only if it is more than 5 percentage points from its observed rate AND the gap is statistically clear after allowing for the number of bands checked: |gap| / sqrt(p(1−p)/n) above the two-sided normal quantile for 0.05 divided by the number of bands checked (Bonferroni; about 3.0 for 20 bands), with p the band's mean forecast. The values are in `evaluation_harness_config.json` (`calibration_tolerance`, rule `slopes-0.90-1.10-bands-30-5pp-bonferroni-v2`) and applied by `evaluation_harness.calibration_check`; a declaration can only name that rule, and a different tolerance needs a reviewed config change first. Locked runs report pass or fail for every candidate and period (`calibration_tolerance_check` in `results.json`).
  - v1 (`slopes-0.90-1.10-bands-30-5pp-v1`, same slopes, a band failed on any gap above 5 points) was replaced on 11 Nov 2026, before any holdout scoring, because it failed even the market reference on noise: every failing band of C, C2, C3, C5, C6 and M on development and validation, M's included, had |gap| / standard error below 2.9, under the Bonferroni bar for the bands checked (2.97–3.04).
- Calibration tolerance, v3 (relative slopes; decided 12 Nov 2026, before any European holdout scoring; applies only to candidates not yet scored, so C6's record stays under v2): each of the candidate's home and away slopes passes if it is between 0.90 and 1.10 OR its distance from 1.0 is smaller than the declared baseline's slope for the same outcome on the same fixtures (both fitted on the fixtures both forecast). The band test is exactly v2's (more than 5 points AND Bonferroni-clear). It is a new named rule in `evaluation_harness_config.json` (`calibration_tolerance_rules`, `slopes-0.90-1.10-or-closer-than-baseline-bands-30-5pp-bonferroni-v3`); `calibration_tolerance` stays v2. A declaration may name either; the verdict passes the baseline's holdout forecasts to `calibration_check`. A baseline can never pass v3 against itself outside the band (its distance is not smaller than its own).
  - Why: on European fixtures the baseline CE is far too sharp (slopes 0.62–0.83), and v2's fixed band would fail a candidate that moves most of the way toward 1 while still below 0.90. v3 asks that the candidate be no worse calibrated than what it would replace.

- Calibration rule for the cagey tier's events, `cagey-events-v1` (decided by Paul on 12 Nov 2026; line set, prices and side choice settled with him on 13 Nov 2026; all before any scoring of D or M on the holdout). A third named rule in `calibration_tolerance_rules`, for D against M only. It applies v3's logic (slope in 0.90–1.10 or closer to 1 than M's on the same events; bands of tenths with at least 30 events failing only when more than 5 points off AND Bonferroni-clear over the family's bands) to two event families, each pooled across its lines; a candidate passes when both pass:
  - (a) narrow: P(|margin| ≤ 1), one event per fixture.
  - (b) no loss on the AH lines the tier can bet. Production rule `no-loss-market-reference-v5` bets any quoted AH line with odds in (1.15, 2.00]; the feed quotes the 25 lines of `asian_handicap.LINES`, −3.00 to +3.00 in quarters (`price_edge_cagey_shortlist.TIER_LINES`, +1.00 to +2.25, belongs to the older v28 rule and is not used). The files quote only the main line, so the main line is priced at the period bookmaker's real quote and every other line at M's fair odds divided by 1 + that bookmaker's average main-line AH margin (Pinnacle 2.70%, 9,452 development and validation matches; Bet365 4.15%, 1,455 retrospective matches; holdout prices never read; frozen in the config, `scripts/cagey_events_margins.py`). One side per fixture, the side whose best bettable line has the higher expected return under D (cost 0); its bettable lines give one event per family floor(line): side margin ≥ −floor(line), i.e. −3 win by 3+, −2 win by 2+, −1 win by 1+, 0 win or draw, +1 lose by at most 1, +2 lose by at most 2, +3 lose by at most 3. D and M are scored on the same events; M checked against itself passes a slope only inside 0.90–1.10.

- Uncertainty: whole calendar weeks are resampled; the 95% interval must be clear of zero.
- Parity test (no waiting): the same match fed through the harness and the live pipeline must give identical probabilities.
- Replay over saved live runs (no waiting): the candidate runs over every forecast frozen since 5 Nov 2026 and must compute cleanly. Integration check only, not evidence of improvement.
- Monitoring after release: the weekly performance reports keep grading every pick, with a rollback trigger if the new model falls behind the old one by a set margin over a set number of matches.
- Rollback trigger for correctness fixes (research v2, v3, v4): after at least 150 graded matches across at least 3 weeks, each version is compared with the previous one on the same frozen inputs, and it is rolled back if its research log loss (AH all lines) is worse with the week-resampled 95% interval entirely above zero. Each graded forecast is replayed under both versions from its own frozen inputs (as the live-replay comparisons do), so the two are scored on the same matches and offers; worse means the new version's log loss minus the previous version's is positive. Rolling back is reverting that version's PR; forecasts frozen under it keep their numbers.
- There is no forward waiting for changes the backtest can test.
- The holdout is scored only with a declaration file (`--declaration`). The declaration names a candidate and baseline registered in the harness, the primary metric, the draw-sensitive lines and the calibration tolerance rule (both must match the config), and the harness applies exactly those. A holdout run scores only the declared candidate, its baseline and the market reference.
- One evaluation per candidate and per frozen setup: the harness fingerprints the scoring code, model files, config and input data, and `evaluation/holdout_ledger.json` refuses a second run of either.
